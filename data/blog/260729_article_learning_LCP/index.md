# Largest Contentful Paint（LCP）とは
LCPとは、3つあるCore Web Vitalsのうちの1つの指標です。

わたしなりの解釈で説明すると、ユーザーがページの表示が完了したと認識するまでの速度のことを言います。
つまり、LCPのスコアが良いということは「初期表示が速いと認識されるページ」ということでもあります。
## ページ読み込み完了ってどのタイミング？
ここでLCPの説明に認識という単語を意図的に使いました。
さて、ユーザーがページを開いて読み込みが完了したと認識するのはどのタイミングだと思いますか？

- ヘッダーの一部が表示されたとき？
- 画面のローディングアイコンが消えたとき？
- 大きな画像が表示されたとき？
- ブログ記事のテキストコンテンツが表示されたとき？

Googleでは、W3Cのフォーラムでの議論や人間の知覚の研究を元に人間がページが読み込みが完了したと認識するタイミングをページの最も大きなコンテンツが表示された瞬間と定義しました。
最も大きなコンテンツが描画されたタイミングなので、Largest Contentful Paintです。
### Contentfulとは
LCPには、Contentfulという形容詞が入っていますがこれは「充実した」「中身が詰まっている」ような意味のようです。
そして、LCPや他のWeb Vitalsの1つである「First Contentful Paint」で使用されている「Contentful」には、ユーザーにとって意味のあるコンテンツという意味合いがあるようです。
なので、もっとも大きな要素だったとしても「ただの背景画像」や「サイズが大きいだけの空っぽの要素」はLargest Contentfulとは言えません。

## LCPの要素となる条件
LCPはScriptでプログラム的に計測するわけですが、実際どのような要素が計測対象になると思いますか？
そもそもLCPはページの完了を認識する速度の指標なので、ユーザーが見ている画面内に表示されない要素はLCPの対象外になります。

たとえば、ヒーローイメージの下にブログのテキストコンテンツがあるようなページでは最初の画面内にはヒーローイメージが占める割合が大きいでしょうから、ページ全体で見たときに大きなコンテンツはブログのテキストコンテンツでも、ヒーローイメージがLCPの対象になります。

{ここに図を投入}

それを踏まえて、LCPの条件は以下になります。（web.devから引用）
>- `<img>` 要素（[最初のフレームの表示時間](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/speed/metrics_changelog/2023_08_lcp.md)は、GIF やアニメーション PNG などのアニメーション コンテンツに使用されます）
> - `<svg>` 要素内の `<image>` 要素
> - `<video>` 要素（ポスター画像の読み込み時間または動画の[最初のフレームの表示時間](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/speed/metrics_changelog/2023_08_lcp.md)のいずれか早い方）
> - [`url()`](https://developer.mozilla.org/docs/Web/CSS/url\(\)) 関数を使用して読み込まれた背景画像を持つ要素（[CSS グラデーション](https://developer.mozilla.org/docs/Web/CSS/CSS_Images/Using_CSS_gradients)ではない）
> - テキストノードや他のインライン レベルのテキスト要素の子要素を含む[ブロックレベル](https://developer.mozilla.org/docs/Web/HTML/Block-level_elements)の要素。


逆に最初の画面内にある特定の要素でも以下のようなものはLCPの対象になりません。（web.devから引用）

> - 不透明度が 0 でユーザーには見えない要素
> - ビューポート全体を覆う要素で、コンテンツではなく背景と見なされる可能性が高いもの
> - ページの実際のコンテンツを反映していない可能性が高い、エントロピーの低いプレースホルダ画像やその他の画像

たしかに、要素サイズが大きくても完全に透明な要素や画面全体を覆っている画像のような要素はユーザーにとって意味あるコンテンツとは言えなさそうです。

まとめると、LCPとは「ユーザーにとって意味のある最も大きなコンテンツが表示されたタイミング」ということになります。

# スコアについて
Googleでは、LCPのスコアをGOOD / NEEDS IMPROVEMENT / POOR の3つに分類しています。
![[01_study/blog/blog/260729_article_learning_LCP/img/good-lcp-values.svg|603]]
画像はweb.devより引用

指標によれば、75パーセンタイルの値でLCPのスコアは2.5秒以内が望ましいとされています。
75パーセンタイルというのは、平たくいうとサイトの利用ユーザーのうち75%はLCPスコア2.5秒を達成できる状態です。
ここからこれらの数値はどのように定義されたのかみていきましょう。
## LCPのスコアはなぜ2.5sがGOODなのか
研究によると、人間がタスクから注意を逸らさずに待てる時間は1秒程度のようです。
（短っ！と思いましたが、近年ではもっと早くなってそうな雰囲気があります。）

1秒程度しか待てないのであれば、LCPのGOODは1秒ではないのかと思いますが、理想を言えば1秒なのでしょうが、Webは技術であり技術には制約があります。

Core Web Vitalsは人間の知覚研究は理想として、現実的に達成可能な指標であることも重要視しています。では、実際にどのような値が達成可能かつ人間の知覚的に理想的なのでしょうか？

世界には数千万のウェブサイトがあります、またそれを利用するユーザーも数千数億と存在しています。実際に公開されているウェブサイトと利用しているユーザーが体験している値がわかれば達成可能な値が分かりそうです。

ここはさすがは世界のGoogleです。GoogleはCrUXというツールで、実際のChromeユーザーの体験データを収集しています。私たちが普段利用しているChromeで利用統計を許可していれば、何気なくブラウジングしていても私たちが体験したパフォーマンスデータがGoogleに蓄えられているわけです。

|     | 1秒   | 1.5秒 | 2秒  | 2.5秒 | 3秒  |
| --- | ---- | ---- | --- | ---- | --- |
| SP  | 3.5% | 13%  | 27% | 42%  | 55% |
| PC  | 6.9% | 19%  | 36% | 51%  | 64% |
web.devより引用 2020 年 4 月現在、LCP 候補のしきい値で「良好」と分類された CrUX オリジンの割合

GoogleがCore Web VitalsのGOODのスコアを決める最低限のルールは、サイトの10%が少なくとも達成できている値であることです。表を見ると、1.5秒の指標では10%ラインはクリアするもののまだ低い水準(SP13%/PC19%)、2秒でも心もとない(SP27%/PC36%)。2.5秒であればSPで42%・PCで51%と、十分現実的に目指せる水準として選ばれたようです。

このように、Core Web Vitalsのスコアの閾値は人間の知覚の研究による理想と現実的な技術の落とし所を絶妙に調整しながら定められています。

# 計測する方法
Core Web Vitalsのスコアを計測する方法は主にGoogleからいくつかの方法が提供されています。

## フィールドとラボ
大きく2つに分けて、フィールドツールとラボツールと呼ばれます。

ツールの前に測定に関して、Googleは測定をラボとフィールドで分けて呼んでいます。
フィールドとは、サイトの実際のユーザーが体験したパフォーマンスのことで、リアルユーザーモニタリング（RUM）データとも呼ばれています。
ラボとは、本番公開前に検証環境用に用意されたデータ・環境で計測されたデータのことです。
Core Web Vitalsではフィールドデータで測定することを重要視しています。なぜなら、フィールドとラボではデータ量もそれぞれのデバイスの性能もネットワークの環境も異なるためです。あと、開発環境は基本的に性能が良いことも多く、開発環境や検証環境では数値に問題がなかったのに、フィールドでは数値が悪かったなんてこともありえます。
