# ウェブバイタルについて
ウェブバイタルとは、Googleが取り組んでいる「ユーザーにとって使いやすいWebサイトを目指す」取り組みのことで、以下のようなアルファベットの略称で表される。
- LCP（Largest Contentful Paint）
- INP（Interaction to Next Paint）
- CLS（Cumulative Layout Shift）
- FCP（First Contentful Paint）
- TTFB（Time to First Byte）
- TTI（Time to Interactive）
これが画期的なのは、各指標が数値で表現されることで、Webサイトの使いやすさをユーザー視点で定量的に評価できるようになったということ。
その点数が高ければ高いほど、ユーザーにとって使いやすいWebサイトと言える。

これらの中でも特に重要な3つの指標がコアウェブバイタルと呼ばれ、Googleが特に重視している。Googleが重視しているということは、SEOにも影響を及ぼす可能性が高い。
## ウェブバイタルのライフサイクル
さっそくコアウェブバイタルの説明をしていこうと言いたいところだが、その前にウェブバイタルが一体どのように定められているのかを知っておこう。ウェブバイタルは常に進化をし続けているのだ。

TC39・WHATWG・IETFなど、ほかの標準策定団体とフローは大きく変わらない。
実験中→検証中→標準化のようなフローで進んでいく。具体的にはこんな感じ。

コアウェブバイタル（CWV）は試験運用版（Experimental）、保留中（Pending）、安定版（Stable）という3つのフェーズで策定される。
![[the-three-lifecycle-phase.svg|697]]
### Experimental
どんな指標も最初はExperimentalから始まる。
指標を計測するのもプログラムだから計測バグがあれば修正するし、指標自体が本来的に意味あるものかも検討される。コミュニティからのフィードバックがめっちゃ重要視されるフェーズ。
INPが登場する以前にインタラクションを計測する指標としてFirst Input Delayという指標があったが、FIDよりINPの方がユーザー体験を計測する上で優れていることはこのフェーズで検証された。
### Pending
Chromeのチームが十分な検証結果を得られたと判断したら、Pendingフェーズに入る。
最低でも6ヶ月間はPendingフェーズにとどまる、その名の通りPendingする。このフェーズ中に、在野のエンジニアたちはこの指標への対応を準備しないといけない。
コミュニティからのフィードバックはこのフェーズでも重要。
### Stable
Pendingフェーズで問題なしと判断された場合は、晴れてStableとなる。
このフェーズでもバグの修正や定義の変更が行われる可能性がある。

ほかの標準化団体と比較すると似たようなフェーズを踏んでいることがわかる。

**TC39（ECMAScript）**
Stage0 → Stage1 → Stage2 → Stage3 → Stage4
**WHATWG**
Stage 0(Proposal) → Stage 1(Incubation) → Stage 2(Iteration) → Stage 3(Committed) → Stage 4(Standard)
**IETF**
Internet Draft → RFC
※IETFは厳密にはもう少し複雑
# コアウェブバイタルについて
上でも述べたが、複数ある指標の中でも最もユーザー体験（Webサイトを通じてユーザーが得る体験）への影響が大きいのが、コアウェブバイタルと呼ばれる3つの指標。
ここではそれぞれの指標について内容を確認していこう。
## LCP
LCPとは、読み込みパフォーマンスの尺度。Largest Contentful Paintの略。
![[lcp-gif.gif]]
ユーザーからすると「ページの読み込みが長いな…」と感じるようなケースで、LCPのスコアは下がるようになっている。
上のGIF画像では、可愛い猫ちゃんのヒーロー画像の読み込みに時間がかかり、表示されるまで待たされている。
### 人間はいつ読み込み完了と感じる？
Googleは、ユーザーはどのようなタイミングで「ページが読み込まれた」と感じるのか？を、さまざまな研究結果から、画面内の最も大きなコンテンツが表示された瞬間に、ユーザーはページの読み込みが完了したと感じると定義した。
だから、Largest Contentful Paint。大きな要素ではなく大きな「コンテンツ」というのもLCPにおけるポイント。たとえば、大きいだけの背景要素が読み込まれても、ユーザーには関係ないと判断する。
## CLS
CLSとは、視覚的な安定性の尺度。Cumulative Layout Shiftの略で、「キュームレイティブ」と読むらしい（ホンマか？）。
![[cls-gif.gif]]
画面の表示時にボタンの位置がガタついている。このガタつきが大きければ大きいほど、CLSのスコアは下がる。
上のGIFでは「カートに入れる」ボタンの位置がずれていて、押そうとした瞬間にボタンの位置が変わってしまったらイライラしそう。
イライラするだけならまだマシなほう。要素の位置がずれて、押そうとしていないボタンをクリックしてしまったら？ そのボタンが決済ボタンだったらどうなる？
## INP
INPとは、応答性の尺度。Interaction to Next Paintの略。
![[inp-gif.gif]]
ボタンを操作しているのに画面への反映が遅くてイライラしているGIF。こちらとしてはボタンを操作したつもりなのに画面に反映されなかったら、どう感じる？あれ、クリックできていなかったのかな？もう1回ポチっと……。

Interaction to Next Paintという名前の通り、ボタンの操作から操作結果が画面に反映されるまでの速度を計る指標がINP。INPの特徴は、ページ滞在中の全イベントが計測対象になるということ。LCPやCLSと違い、ロード直後だけでは指標の数値がわからない。

# 各指標のスコアと計測方法
冒頭でウェブバイタルは良し悪しがスコアで評価できると説明したが、LCP・CLS・INPそれぞれの評価がこちら。
![[01_study/blog/blog/260718_about_core_web_vitals/img/good-lcp-values.svg|697]]
![[01_study/blog/blog/260718_about_core_web_vitals/img/good-cls-values.svg|697]]
![[01_study/blog/blog/260718_about_core_web_vitals/img/inp-desktop-v2.svg|697]]
画像はWeb.devより拝借。※ダークモードだと少し見づらいかも…。

ざっくり見ると、「良好」「改善が必要」「不良」の3つに分かれていて、それぞれ閾値で区切られている。さらに、Googleはページ読み込みの75パーセンタイルを測定して、良好のスコアを得られる状態にしておくべき、と説明している。
## 75パーセンタイルとは
パーセンタイルは統計用語。僕自身そこまで統計に明るくないので、パッとイメージがつかなかったので、ここで簡単に説明しておく。

定義はこれ
> 計測値の分布（ばらつき）を小さい数字から大きい数字に並べ変え、パーセント表示することによって、小さい数字から大きな数字に並べ変えた計測値においてどこに位置するのかを測定する単位。

要はこんな感じ。
たとえば、100個のWebサイトの読み込み速度を計測したデータがあるとする。
さまざまな環境やデバイスで読み込まれた速度なので、当然ばらつきが出ている。
この100個のデータを速い順に並び替えて、75番目の速さのデータを75パーセンタイルと呼ぶらしい。もちろんパーセンタイルなので、総データ数が1000になれば750番目だし、10000になれば7500番目。
![[percentile_75_illustration.svg|697]]

つまり、Googleが言う「75パーセンタイルで良好を満たすべき」というのは、Webサイトにアクセスする75パーセント以上の人が快適に閲覧できる状態を指している。
## それぞれの指標、閾値
指標に対する閾値、たとえばLCPであれば2.5秒と4秒は、どうやって決まっているのか？
これに関しても説明しておこう。
いずれも決められ方は似ているので、代表してLCPで解説をする。

2つの基準で決められる。
- 人間の知覚に関する研究
- 技術的な実現可能性
### 人間の知覚
コアウェブバイタルは人間にとって使いやすいWebサイトになっているかどうかの指標なので、当然人間の知覚に関する研究が重要。
人間の知覚と言っているのは、画面がフリーズしたと感じる秒数とか画面が乱れたと感じる動きなど。
これらは日々研究されていて、たとえば、「フォーカスを失うまでに待機できるのは1秒程度」「ボタンをクリックしてから画面が反応するまでに0.2秒以内じゃないと不自然に感じる」とか、色々ある。
### 実現可能性
いくら人間が0.2秒以内じゃないと不自然に感じると言っても、Webサイトは魔法ではない。
技術的に不可能なものは指標にしても何の役にも立たない。
そこで、Googleが日々収集しているフィールドデータから、いくつかのサイトですでに達成されている値の中から選ぶ。少なくとも10%のWebサイトで達成されていることが最低限の基準になっていて、あとはいい塩梅を目指すということ。
#### フィールドデータ
フィールドデータを簡単に説明する。
GoogleはChromeを通じてWebサイトのパフォーマンスデータを収集している。もちろん収集を許可したユーザーのみ。Chromeを利用するユーザーが訪れたさまざまなサイトで、ユーザーが実際に体験した生のパフォーマンスデータをフィールドデータと呼んでいる。
そのフィールドデータは我々にも公開されており、さまざまなツールから参照することができる。これはChrome DevToolsのパフォーマンスタブで確認したもの。
![[01_study/blog/blog/260718_about_core_web_vitals/img/dev-tools-field.png]]
これとは別にラボデータというものもあり、別記事で解説を行う予定。
## 実際にLCPはどのように決められたのか
これまでの情報からLCPがどのように決められたのかを最後に見ておこう。
![[01_study/blog/blog/260718_about_core_web_vitals/img/good-lcp-values.svg|697]]

まず、人間の知覚。
研究によるとユーザーが画面への注目を失うまでに待機できる時間は0.3秒〜3秒らしい。（現代人はもっと短くなっていそうだが…。）
LCP観点で言うと、画面のメインコンテンツが0.3秒以内で表示されるのが良さそう。そして、3秒以上だとダメそう。
LCPの場合は、2.5秒以内が良好で4秒以上が不良なので、実際にそれに近い値になっていることがわかる。

次に、実現可能性。
ここでフィールドデータが登場する。

|      | 1秒   | 1.5秒 | 2秒  | 2.5秒 | 3秒  |
| ---- | ---- | ---- | --- | ---- | --- |
| モバイル | 3.5% | 13%  | 27% | 42%  | 55% |
| パソコン | 6.9% | 19%  | 36% | 51%  | 64% |

Web.devから拝借している。
たとえばこの表の「モバイル・2.5秒」の列は、こう読む。
LCPが2.5秒未満というスコアを75パーセンタイルの値で達成しているWebサイトが42%ある。
要は、2.5秒を「良好」の基準にすれば、現時点でモバイルは42%、パソコンは51%が達成しているということ。
これは、「少なくとも10%のWebサイトで達成済み」という最低基準の条件も満たしている。
さらに、パフォーマンス上位のサイトが75パーセンタイルで達成可能な値を目指した結果、常に達成可能だったのが2.5秒だったということ。
# コアウェブバイタルを測定する
コアウェブバイタルはGoogleが提供しているさまざまな無料ツールで測定することができる。
## Chrome DevTools
![[01_study/blog/blog/260718_about_core_web_vitals/img/dev-tools-field.png]]
Google Chromeのパフォーマンスタブで確認することができる。
フィールドデータに関しては、十分なデータがあるサイトのみ表示される。当然だが、アクセスの少ないWebサイトはデータ量が不十分ということで表示されない。
## PageSpeed Insights
PageSpeed Insightsは、過去28日間のページレベルとオリジン（サイト）レベルのパフォーマンスレポートを作成してくれる。
スコアの低い指標については改善のヒントもくれる。
![[page-speed-insight.png]]
## Search Console
ページ単位のパフォーマンスレポートを作成できる。
PageSpeed Insightsがどのサイトでも利用できるのに対して、Search Consoleは自分が所有者のページしか計測できない。
過去のパフォーマンスデータも確認することができる。
## CrUx Vis
CrUX History APIをベースに構築されたWebツールで、Web Vitalsの全指標について過去から現在までの推移を見ることができる。
## Lighthouse
灯台（Lighthouse）というツールでも計測できる。
これはいろんな場所から実行できる。
Chrome DevToolsの中にもあるし、
![[01_study/blog/blog/260718_about_core_web_vitals/img/light-house.png]]
Chromeの拡張としても存在する。
![[chrome-add-on.png|456]]
特徴的なのは、Lighthouse CIというnpmパッケージも公開されている点。CIを組めば、PRごとにLighthouseを回すといったことも可能になる。
ただし、Lighthouse CIは実行に時間がかかることがあるので、実行時間に制限がある環境では注意が必要。
