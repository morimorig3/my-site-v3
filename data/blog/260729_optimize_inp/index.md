復習
INPはユーザーがページに訪れている間に発生した対象インタラクションのページの応答性を計測する
目標は75%のアクセスでINP=200を達成すること
![[inp-desktop-v2.svg|697]]

INPが低い原因となりそうなこと
基本はフィールド→ラボの流れ
フィールド計測で遅いデータを特定するラボで計測しながら改善させる

まずはデータ収集
フィールドで収集することが重要
実際に本番のユーザーがどの程度の体験をしているかを知るための唯一の手段がフィールドだから、しかもCrUXのようなRUMツールはINPの値になったインタラクションのヒントとなる情報をくれる

ラボで遅いイランタラクションを調べる
一般的なユーザーの操作シナリオをやって遅い箇所を特定する
読み込み中にページを操作するとか
読み込み中のページ操作はメインスレッドが仕事中なことが多いからINPの原因になりがち（ページを操作できることが問題なのか？）

遅いインタラクションが特定できた
インタラクションとはどこからどこまでのことを指しているのか
![[01_study/blog/blog/260729_optimize_inp/img/whats-in-an-interaction.svg|697]]
1. ユーザーの操作が発生
2. 操作からイベント発生までの遅延
3. 処理時間（一般的にはJS）
4. 操作の結果の画面描画が完了するまでの遅延

2~3の時間をできる限り小さくすることが目標

入力遅延
操作してから処理が開始するまでの遅延
静の待機状態から操作を行うとおそらくこれは0になる
しかし、他の操作をしててJSのメインスレッドが動いている時に操作をすると
直ちにイベントは発生しない そこが遅延となる

入力遅延：詳解
入力遅延はユーザーが画面をクリックしてから
イベントのコールバックが発生するまでの時間
![[a-simplified-visualizatio-d1514b424d9ec_1920.png|410]]
チューニングできる遅延・できない遅延

できない遅延
OSが入力イベントを検知してブラウザに渡すには一定の遅延が発生する

できる遅延
ページ自体で発生する他のことが原因で発生している遅延
ページ自体をチューニングすることでなんとかできるかもしれない

遅延となりがちな原因
- メインスレッドでタイマー処理をしている
- 長いタスクを処理している
- インタラクションが重複している
- デカすぎるJSサイズ（バンドル時など）

メインスレッドでタイマー処理をしている
JSで頻繁に使用される`setTimeout`と`setInterval`は入力遅延の原因になりがち
これらのコールバックが処理されるタイミングはJSにスレッドを占領されるので、ユーザーが操作したタイミングとタイマーがコールバックを処理しているタイミングが重なると入力遅延になる
これが自分のコード起因だと減らすかやらないかとチューニングできるけど、残念なことにサードパーティのJSでやられていたらお手上げ

長いタスクを処理している
メインスレッドでメチャクチャ処理に時間がかかるタスクを実行していたら
その時に操作をした場合遅延が発生する
![[a-visualization-how-long-af65d3963b8fb_1920.png]]
[長いタスクを分割する](https://web.dev/articles/optimize-long-tasks?hl=ja)ことで回避することができる

インタラクションが重複している
これは解決が難しい
なぜなら重複する原因がユーザーの操作であることが多いから
たくさんのボタンをクリックしたり、キーボード操作をしたり
フォーム入力が発生するようなUIではよく起こる原因
例えば、クリックでfetchが走るようなボタンを連打されると・・・？
できること
- 入力ハンドラをデバウンスしてイベントコールバックが実行される回数を間引く
- AbortControllerを利用して必要のないfetchをキャンセルする
- 可能な限りCSSのアニメーションを利用する


イベントコールバックを最適化する
重要なことはコールバック内でやることを小さくする

頻繁にメインスレッドに処理を譲る
軽い処理はすぐに実行
重い処理はsetTimeoutで送らせて実行など
処理を細かく分割することで遅延を減らすヒントになるかもしれない

レンダリング作業を早めに実行できるようにする
メチャクチャチューニングするケース

イベントコールバックのコードを構造化する
すぐにする処理＝ビジュアルに関係するもの
後で実行する処理＝時間のかかる処理

リッチテキストエディタで入力のたびに保存が走るようなUIは考えただけで、イベントが大量に走ってブロッキングされそうだ
1. ユーザーが入力した内容でテキストボックスの更新スタイルの更新
2. 現在の単語数を表示するUIの更新
3. スペルミスを確認するロジックの更新
4. 最新の変更の保存（ローカルまたはDB）
すぐさま更新しなければいけないのは1番だけ
他の3つは後でやればいい
```js
textBox.addEventListener('input', (inputEvent) => {
  // Update the UI immediately, so the changes the user made
  // are visible as soon as the next frame is presented.
  updateTextBox(inputEvent);

  // Use `setTimeout` to defer all other work until at least the next
  // frame by queuing a task in a `requestAnimationFrame()` callback.
  requestAnimationFrame(() => {
    setTimeout(() => {
      const text = textBox.textContent;
      updateWordCount(text);
      checkSpelling(text);
      saveChanges(text);
    }, 0);
  });
});
```
同期的にテキストだけ更新をして、一度メインスレッドに処理を譲ってから残りの処理は後で処理を行う
![[interaction-latency_1920.png]]
一度にまとめてやっていると全ての処理が完了するまでテキストの入力は見えないが
先にメインスレッドにレンダリングを行う余地を与えているので、画面の変化が早く感じられる
楽観的更新と呼ばれるものもこれに近い

レイアウトスラッシングを回避する
JavaScriptから要素の高さや位置を取得しようとしたときに、JavaScriptは正確な情報を取得しようとして要素を強制的にレンダリングする
具体的にはJSでスタイルを変更してから、変更後のスタイルをすぐさまそのタスクないで取得しようとすると発生してしまう

表示の遅延を最小限に抑える
インタラクションの表示遅延はイベントのコールバック完了後からブラウザが視覚的な変化を示す次のフレームが描画できるまでの時間

できること
- DOMサイズを最小限に抑える
- JSでHTMLをレンダリングするコストに注意する
- `content-visibility`で画面外の要素を遅延レンダリングする

DOMサイズを小さくする
当たり前だがDOMサイズが小さければレンダリングが早く、大きければ遅い
小さくできるならできる限り小さい方がいい
でも限界はある
- [DOMサイズを減らす努力](https://web.dev/articles/dom-size-and-interactivity)をしてみたり
- ユーザー操作中にDOM追加する

`content-visibility`を使う
これを使えば要素がビューポートに近づくにつれて遅延レンダリングを行うのと同等のことができるらしい
https://web.dev/articles/content-visibility?hl=ja

JSでHTMLをレンダリングするコスト
HTMLレンダリングのコスト
1. HTML解析 HTMLをDOMに解析
2. DOMにスタイルを適用する
3. レイアウトを計算する
4. レイアウトをレンダリングする
以上が避けられないコスト

サーバーからHTMLファイルが送られるとそれはストリームで届く
ストリームというのは1つのファイルが細切れ（チャンク単位）になって届くということ
ブラウザは増分を解析していくので読み込み中に定期的に自動で暗黙的にyieldしていくから開発者が気にせず利用できる無料の最適化

SPAと呼ばれるモデルでは
HTMLファイルは最小単位の本当に小さいもの
これには欠点があって、JSで全てのHTMLを組み立てるのでそれをブラウザが解析してスタイルをあててレイアウトするまで処理が終わらないということ

クライアントで大量のHTMLをレンダリングしようとすると次のフレームの処理が遅れることもあるので注意しなければならない
