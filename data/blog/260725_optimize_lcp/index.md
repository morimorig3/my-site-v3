LCPはメインコンテンツが読み込まれるまでの速度
計測対象はビューポート内の画像またはテキストコンテンツ
つまりファーストビュー内の画像やテキストコンテンツってこと
サイトの75%以上の読み込みでLCPの読み込み速度2.5秒以内を達成することが目標
＝ユーザーにとって良い
![[good-lcp-values.svg|650]]
まずLCPに問題があるかどうかを確認する
一番大事なことは実際にユーザーが体験しているデータを計測すること
難しい場合はラボツール（Lighthouseなど）を使う
1. RUMツールを使う
2. ラボ計測ツールを使う
3. CrUXデータを使う
CrUXデータというのはGoogleが収集している普段のユーザーが体感しているパフォーマンスレポートのようなもの
## Chrome Dev Tools パフォーマンスタブ
Chromeはユーザーのパフォーマンスを計測しているので
Chrome DevToolを利用すれば実際のユーザーがどれくらいの数値を出しているのか確認することができる
![[field-lcp.png]]
## PageSpeed InsightsのCrUXデータ
実際のユーザーの環境で評価するという項目はCrUXのデータが表示されている
![[page-speed-insights.png]]

Chrome Dev ToolsでもPageSpeedInsightsでもページに十分なアクセスがないと当たり前だが計測できないので注意
その場合はページ上で実行される計測用のAPIをJavaScript経由で実行して計測することになる
CrUXにデータがあるサイトはPageSpeed Insightsでは常にCrUXのデータが表示される

LCPの最適化を目指すときに重要な指標は？
FCPとTTFBの値が重要
FCPとTTFBの値がLCPのスコアに影響してくるイメージ

TTFBとはなんじゃい？
Time to First Byteで、サイトの訪問者がリンクをクリックしてからHTMLドキュメント群の最初の1バイト目を受診するまでの時間なので
そもそもTTFBが2.5秒かかってたらLCPは達成不可能な指標になってしまう
TTFBが悪いのには複数の要因がある
- サーバーのリダイレクトが複数行われてたり
- オリジンサーバーから遠いところにユーザーがいたり
- シンプルにネットワークの状況が悪かったり
- クエリパラメータ起因でキャッシュコンテンツを使えないなど

晴れてTTFBが完了したら、ようやくレンダリング開始
最初にレンダリングされるコンテンツはFirst Contentful Paintとして計測される
Contentful という名前の通りただの要素のかけらではなくて、ページのコンテンツと思われるものがペイントされた時間を計測する

FCPとTTFBに差がある
もし、1バイト目受診開始からFCPが長い場合はその間に色々ダウンロードする時間があるってこと
FCPとLCPに差がある
たとえば、LCP要素が最初のHTMLに存在しておらずJS経由でレンダリングされるとか

注目するもの2つ
- 最初のHTMLドキュメント
- LCP リソース
他の要素も影響するけど特にこの2つの要素がLCPにとって重要

LCPリソースの特定にはDev ToolsなりPageSpeedなり計測ツールで簡単に特定することができる

これは一般的なページのネットワークウォーターフォール図でこの図ではLCPのためのリソースが画像になっている
LCPのためのリソース読み込みが完了したらできるだけ早く先に表示してあげることが重要
![[a-network-waterfall.png]]

LCPの合計時間が次のように分割することができる
1. #1 Time To First Byte
2. #2 リソース読み込みの遅延
3. #3 リソースの読み込み時間
4. #4 要素のレンダリング遅延
LCPを最適化するにはこれらを1つずつ最適化していく作業である
![[lcp-breakdown-four-subparts_1920.png]]
注意なのがこれらを全てを圧縮する必要があるということ
たとえば、リソース読み込み時間を減らすためにリソースを圧縮して渡しても要素をレンダリングするまでには解凍する必要があるから他のブロックに遅延が移動するだけで意味がない

遅延系（リソースの読み込み遅延、要素のレンダリング遅延）の2つの項目は0を目指す
時関係は本質的に減らすことが難しい（技術のブレークスルーなどない限り）
遅延系は技術で解決することができる可能性がある
この割合を目指そう
```
LCP(100%) = TTFB(40%) +
			Resources load duration(40%) +
			Element Render Delay(10%) + 
			Resources load Delay(10%)
```
サマライズするとLCPの大部分はHTMLドキュメントとLCPリソースの読み込み時間に費やされるべきここはボトルネック

改善その1
リソースの読み込み遅延を改善する
理論上、最速でLCPリソースの読み込みを開始可能なのはTTFBの直後だが
実際はLCPリソースが読み込まれるまでに遅延が必ず存在する
![[a-network-waterfall-diagr-improve.png]]
このウォーターフォール図ではLCPリソースの前に紫色のバーで示されているように別のリソースが読み込まれている
LCPリソースの読み込み速度・順番に関係する実装は以下
- リソースが検出された日時
- リソースに付与される優先順位
ブラウザはHTMLファイルをスキャンすることで必要なリソースを検出する
HTMLファイルのプリロードスキャナで見つけられるパターン
- LCP要素がimg要素かつsrc属性またはsrcset属性が初期HTMLアークアップに記載
- LCP要素がCSSの背景画像、Webフォント要素の場合<link rel="preload">やLinkヘッダーでプリロード
HTMLファイルのプリロードスキャンで見つけられないパターン
- JSを利用してどう的に追加されるimg要素
- JSで遅延読み込みするimg要素
- CSSの背景要素
これらはJSのスクリプト実施後やスタイルシートの適用後にLCPリソースの読み込みが開始される

遅延読み込みをなくす第一はHTMLの初期状態からリソースを検出可能な状態にすること
外部のCSSやJSから読み込む場合はpreloadかつ優先度高で読み込みをすべき
```html
<!-- Load the stylesheet that will reference the LCP image. -->
<link rel="stylesheet" href="/path/to/styles.css">

<!-- Preload the LCP image with a high fetchpriority so it starts loading with the stylesheet. -->
<link rel="preload" fetchpriority="high" as="image" href="/path/to/hero-image.webp" type="image/webp">
```
画像はfetchpriority属性で重要なリソースであることを示すことができる
```html
<img fetchpriority="high" src="/path/to/hero-image.webp">
```
lowも設定できる　複数にhighを設定すると意味がないので
```html
<img fetchpriority="low" src="/path/to/carousel-slide-3.webp">
```
カルーセルの3枚目とかは優先度を下げるなど
適切にLCP要素の優先度を調整することでリソースの読み込み遅延を改善することができる
![[a-network-waterfall-diagr-improved.png]]

その2
要素のレンダリング遅延を改善する
LCPリソースが読み込まれるタイミングは最適になりました
それではすぐさまLCPリソースをレンダリングしましょう

リソースが読み込み済みなのにレンダリングされない理由
- headタグ内のスタイルシートや同期JavaScriptが読み込まれていてページのレンダリングがブロックされている
- リソースは読み込み完了したがDOMに追加されていない
- 要素が非表示になってる
- 長時間実行タスクのせいでメインスレッドがブロックされて、レンダリングタスクが待機状態になっている

スタイルシートはすべてのコンテンツのレンダリングをブロックする
そりゃそうで、スタイルシートを読み込んでおかないとブラウザデフォルトスタイルの要素が画面に描画されちゃうから
クソデカCSSになっててLCPリソースの読み込みよりスタイルシートの読み込みが遅くなっているようであれば
ギチギチにチューニングしようと思えばできること・・・
- 未使用のCSSを徹底的に削除する
- 重要ではないCSSの読み込みだけ遅延させる
- CSSを圧縮して最小化して通信サイズを小さくする
	- スタイル名をハッシュかするとか

JavaScriptはレンダリングを妨げる
deferではない、asyncでもないJavaScriptの処理はレンダリングをブロックして処理を続ける
headタグ内にdeferでもasyncでもない同期的なJavaScriptを入れる必要はほとんどない
早い段階で実行しとかなきゃいけないような処理はインライン化しておくのがベスト
別ファイルにして配信するとネットワーク遅延が発生する
<head>
  <script>
    // Inline script contents directly in the HTML.
    // IMPORTANT: only do this for very small scripts.
  </script>
</head>

SSRする
メリット
- JSで動的に画像を定めている場合などはSSRして初期HTMLに画像URLを含めることで検出可能になる
- 追加でページ構築のためのJSを実行する必要がなくなる
デメリット
- TTFBが長くなる可能性がある
	- サーバーの性能は管理できるが、ユーザーのトラフィックや端末の性能は管理できないので価値があるトレードオフ
SSGもパフォーマンスの面では優れた選択肢

大事なこととして、ブラウザはメインスレッドで画像をレンダリングするので、メインスレッドでJSが実行されていたらレンダリングもブロックされる

ここからは改善の難しい次関係

その3
リソースの読み込み時間
できることはあんまりない
- リソースのサイズを小さくする
- リソースの移動距離を縮小する
- ネットワーク帯域幅の競合を減らす
- ネットワーク時間を完全になくす

リソースのサイズを小さくする
LCPは画像かウェブフォントなのでそれぞれ小さくしたり最適なフォーマットを使ったりする
限界はある
- 最適な画像サイズにする（大きすぎず・小さすぎない）
- 最適な画像フォーマットにする（Webp使え！）
- 画像を圧縮せよ
- ウェブフォントを小さくする（使ってないウェイト落とせ）

リソースの移動距離を縮小する
これはCDNを使うくらいしかやりようがない
画像CDNはリソースの移動距離を短縮するだけじゃなくてリソースのサイズも小さくなるので、自動的にリソースのサイズ縮小という機能もこなすことができる

CDNを利用するからといってサードパーティドメインから配信すると接続コストが高くつく
HTMLと同じドメインから配信するのが最善の方法
オリジンからCDNへのリクエストをプロキシできるサービスがあるので利用できるならばそうするべきである

ネットワーク帯域の競合を減らす
同時にリソースを読み込んでいると1つだけ読み込んでいる時より時間がかかることがある
LCPリソースにfetchpriorityをhighに指定することでできるだけ早く読み込みを開始するように指示すると
ブラウザはLCPリソースと他のリソースが競合しないように努力してくれる
ただ、fetchpriorityがhighのものが複数あったり、そもそもめちゃくちゃ多いリソースを読み込んでいる場合はLCPリソースの読み込み速度が遅くなる

ネットワーク時間を改善になくす
キャッシュ設定をしてリソースを配信することで1回目は無理だが2回目以降はリソースをキャッシュから読み込ませることでネットワーク時間が0になる

ウェブフォントの場合はfont-displayをautoにしておけばテキストが読み込み中でも常にデフォルトフォントで表示される

もし、LCPリソースが小さいならばdata URLに変換してインライン化すればリクエスト不要になるけど
まあそれはそれでリソースがキャッシュされなくなるのでトレードオフが発生する

その4
TTFBを短縮する
初期HTMLをできる限り早く配信する
でもまあ開発者が制御できることではないことが多い

よくあるTTFBが遅くなる理由は広告や短縮リンクで複数回リダイレクトされている場合
また、分析用のクエリパラメータなどでキャッシュされたコンテンツじゃなくて全てをオリジンサーバーから取得している時など

LCPがどうやって計測されているのか
いくつかのRUMツールで計測可能であるがいずれのRUMツールも以下のAPIを通じてLCPを計測している
- Larget Contentful Paint API
- Navigation Timing API
- Resources Timing API

まとめ
LCPは複雑・いろんな要因の影響を受ける
注意することはLCPリソースの読み込みを最適化すれば良い
1. LCPリソースは可能な限り早く読み込み開始しましょう
2. LCP要素のリソースの読み込みが完了したらすぐにレンダリングしましょう
3. 品質を損なうことなくLCPリソースの読み込み時間をできる限り早くしよう
4. 最初のHTMLドキュメントをできる限り早く配信しよう
